# Metrics API

Standalone HTTP API that queries DevLake’s MySQL and returns pre-computed PR metrics for the developer dashboards. Lives under `backend/plugins/metrics/` as an independent binary (not registered in the DevLake plugin framework).

---

## Why this exists

### n8n maintenance problems

We were maintaining PR metrics as n8n workflows and hit several issues:

| Problem | Impact |
|---|---|
| No unit tests | Logic regressions land in production |
| Changes made directly in production | No review, no rollback story |
| Incomplete version control | Backups often only saved the “Process Data” node; other nodes (`Get PRs`, etc.) drifted unnoticed |
| Duplicated functions | `calculateMedian`, `isAutogenerated`, `isBotReview` copied across workflows |
| Duplicated nodes | `Get PRs`, `Normalize Input`, etc. repeated per workflow |

Together: hard to track changes, easy to ship bugs, expensive to evolve.

### Approach: standalone HTTP API in Go

Replace the n8n metric computation with a Go service that:

1. Reads from the same DevLake MySQL domain tables
2. Applies shared query + transform logic once
3. Exposes dashboard-ready JSON over HTTP


### Where it lives

| Criteria | DevLake plugin dir | n8n-pulumi-poc | New repo |
|---|---|---|---|
| Deployment coupling | Separate from infra | Co-located with Pulumi | Separate from infra |
| Schema proximity | Schema changes visible immediately | Cross-repo drift risk | Cross-repo drift risk |
| Maintainability | Existing repo | Existing repo | Third repo to maintain |

**Choice: DevLake plugin directory** (`backend/plugins/metrics/`).

Data collection (DevLake) and metric processing stay in one place. Schema changes and domain models are co-located. The binary is still **standalone** — built separately, not loaded by the DevLake server plugin loader.

### Performance bar

Maintainability is the primary win. Performance must stay **equal or better** than the n8n path (same SQL surface, less JS overhead, connection pooling, pure transforms).

### Request pipeline

## Routes

Base path: `/api/metrics/<category>/<name>`

All metric endpoints are **POST** with the same JSON body.

| Method | Path | Chart `type` | What it returns |
|---|---|---|---|
| `GET` | `/healthz` | — | `{"status":"ok"}` (DB ping) |
| `POST` | `/api/metrics/pr/key-metrics` | `stats` | Throughput, median cycle time, opened PRs, outlier PRs (+ period compare when ≤30d) |
| `POST` | `/api/metrics/pr/stages` | `doughnut` | Time spent in PR lifecycle stages |
| `POST` | `/api/metrics/pr/cycle-time` | `line` | Daily median cycle time + 7-day rolling avg |
| `POST` | `/api/metrics/pr/productivity` | `doughnut` | Author productivity distribution |
| `POST` | `/api/metrics/pr/flow` | `sankey` | PR lifecycle flow (needs PRs + reviews) |
| `POST` | `/api/metrics/pr/z-score` | `bar` | Cycle-time z-score buckets vs 90-day lookback |
| `POST` | `/api/metrics/pr/scatter` | `line` | Cycle time distribution buckets (merged vs abandoned) |

Unregistered `/api/metrics/...` paths return `501 Not Implemented`.

### Handler → query → transform map

| Route | Queries | Transform |
|---|---|---|
| `key-metrics` | `KeyMetricsStats`, optional previous-period stats, `KeyMetricsOutliers` | `BuildKeyMetrics` |
| `stages` | `StagesPRs` | `BuildStages` |
| `cycle-time` | `BasePRs` | `BuildCycleTime` |
| `productivity` | `BasePRs` | `BuildProductivity` |
| `flow` | `BasePRs`, `Reviews` | `BuildFlow` |
| `z-score` | `BasePRs` (current) + `BasePRs` (90d lookback) | `BuildZScore` |
| `scatter` | `BasePRs` | `BuildScatter` |

## Request body

Same shape for every PR metric endpoint (mirrors dashboard `buildDiagramRequest()`):

```json
{
  "owner": ["redhat-developer"],
  "name": ["rhdh"],
  "from": 1700000000,
  "to": 1702000000,
  "blueprintid": "72",
  "connectionid": "1",
  "jiraproject": "",
  "projects": [],
  "userwhitelist": [],
  "teamrepos": [],
  "projectname": "PRCT - Team"
}
```

| Field | Notes |
|---|---|
| `owner` / `name` | Parallel arrays; zipped to `owner/name` repo IDs |
| `from` / `to` | Unix seconds |
| `blueprintid` | DevLake blueprint ID (project scoping via `project_mapping`) |
| `userwhitelist` | Optional author filter |
| `teamrepos` | Fallback repo list if `owner`/`name` empty (already full `owner/name`) |

Handlers convert this via `toParams()` into `query/pr.Params`.

---

## Response shape

Every endpoint returns a `MetricResponse` (`model/response.go`):

```json
{
  "type": "stats|doughnut|line|bar|sankey",
  "subtype": "optional",
  "label": "...",
  "description": "...",
  "lastupdate": 1700000000000,
  "data": {},
  "options": {},
  "summary": {},
  "warning": ""
}
```

The dashboard picks a renderer from `type` and feeds `data` (+ `options` when present) to Chart.js or a custom widget. Drill-downs use `extra` / `ExtraData` (openList configs + PR rows).

## Build & run

```bash
cd backend
make build-metrics-api

export MYSQL_HOST=<MYSQL_HOST>
export MYSQL_PORT=<MYSQL_PORT>
export MYSQL_USER=<MYSQL_USER>
export MYSQL_PASS=<MYSQL_PASS>
export MYSQL_DB=<MYSQL_DB>
export METRICS_ADDR=:<METRICS_ADDR>
export METRICS_ALLOWED_ORIGIN=<METRICS_ALLOWED_ORIGIN>

./bin/metrics-api
```


```bash
cd backend
podman build -f plugins/metrics/Dockerfile -t metrics-api .

# Run (MySQL on host / compose — use host.containers.internal on macOS)
podman run --rm -p 8181:8181 \
  -e MYSQL_HOST=host.containers.internal \
  -e MYSQL_PORT=<MYSQL_PORT> \
  -e MYSQL_USER=<MYSQL_USER> \
  -e MYSQL_PASS=<MYSQL_PASS> \
  -e MYSQL_DB=<MYSQL_DB> \
  -e METRICS_ADDR=:8181 \
  -e METRICS_ALLOWED_ORIGIN=<METRICS_ALLOWED_ORIGIN> \
  metrics-api

# Tests / lint
go test ./plugins/metrics/... -v
golangci-lint run ./plugins/metrics/...
```

Excluded from `build-plugins.sh`.

## Adding a new PR metric

1. Add SQL in `query/pr/queries.go` (and row type in `rows.go` if needed)
2. Add pure `BuildFoo` in `transform/pr/` + table tests
3. Add handler under `api/routes/pr/handlers/`
4. Register in `api/routes/pr/register.go`
5. Document the route in this file
